


**★ A green suite does not mean a correct FORM — assert the box, not just the number.** V266: Schedule 1-A Part V put the right deduction in the wrong boxes for every senior (6,000 in box 35, a bare "1" in box 36a, the deduction in the spouse's 36b, box 38 blank) while Form 1040 line 13b, the tax and the refund were all exactly right. 1,590 e2e and 2,428 unit tests saw nothing, because they assert values and this was a *placement* defect. When a form's rendering is in question, verify geometrically: pull each widget's rect from the AcroForm and match it to the printed label beside it. That check cleared Parts I-IV in one pass and isolated the four wrong fields.

**★ `scripts/schedule-mappings/*.json` is HAND-CURATED — an off-by-one there silently shifts every later box.** The generator faithfully reproduces whatever the curated file says, and the CSV, the semantic PDF and `elements.json` all inherit it, so a single wrong line propagates to four artifacts across three repos. It also invented a field the form does not have (`line36_qualifying_senior_count`); **if a semantic name has no counterpart in the printed form, that is the bug, not a naming quirk.** [[feedback_fields_map_must_be_built_from_the_finished_model]]

**★ When you rename a field's meaning, rename the field.** Line 35's column held the unreduced $6,000 while being drawn into a box the form defines as the amount *after* the phaseout. Repointing the value and leaving the name as "base" would have rebuilt the same trap for the next reader — so V266 renames the column with it. A column named for something the form never prints has no legitimate box to render into, which is how it ends up in the wrong one. [[feedback_field_named_for_a_line_is_an_unchecked_claim]]
